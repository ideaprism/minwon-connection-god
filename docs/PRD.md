## 0. v1 대비 무엇이 바뀌었나

v1은 "무엇을 만들 것인가"는 잘 담았지만, **경기로 성립시키는 데 필요한 규칙과 방어 장치**가 비어 있었습니다. v2에서 채운 것은 다음 9가지입니다.

| # | v1의 문제 | v2의 해결 | 근거 |
| --- | --- | --- | --- |
| 1 | 최종 점수를 클라이언트가 계산해 서버로 전송 | **서버 권위 채점**(§7) — 서버가 문항 시퀀스를 발급하고, 입력 로그를 재생해 점수를 재계산 | 참가자가 전원 개발자. 브라우저 콘솔로 점수 조작이 가능한 구조는 대회로 성립하지 않음 |
| 2 | 점수 체계 미정의 | 정답·콤보·속도·페널티 **수식 확정**(§4.2) | 배점이 없으면 난이도·변별력 검증 불가 |
| 3 | 난이도 고정(180초 단일 구간) | **3페이즈 난이도 곡선**(§4.3) | 실력 변별이 안 되면 순위가 운으로 결정됨 |
| 4 | 찬스 소진 후 악성 민원인 등장 시 대응 수단 없음 | **데드락 3중 차단**(§4.5) | v1 규칙 그대로면 게임이 멈춤 |
| 5 | 오답 = 감점 + 1.5초 스턴 + 콤보 리셋 (3중 처벌) | 스턴 0.7초 + 콤보 리셋으로 단일화, 감점 폐지(§4.4) | 초보자 이탈 방지, 음수 점수 방지, 관전 시 정지 화면 최소화 |
| 6 | 개발 목적은 "타 부서 업무 이해"인데 학습 피드백 없음 | **오답 시 정답 부서 + 한 줄 해설 노출**(§5.3) | 목적과 기능이 연결되지 않은 상태였음 |
| 7 | 관람자가 대상 고객인데 관전 화면 요구사항 없음 | **관전 모드 + 대형 스크린 스코어보드**(§6) | e스포츠는 보는 재미가 절반 |
| 8 | 사번·성명을 공개 스코어보드에 노출 | **표시명/부서만 공개, 사번은 해시 저장**(§8) | 개인정보보호법 적용 대상 |
| 9 | 화면 전체 번쩍임·흔들림 연출 | **광과민성 안전 기준 + `prefers-reduced-motion`**(§5.5) | 전사 대상 행사에서 실제 건강 리스크 |

## 1. 제품 개요

* **장르**: 캐주얼 오피스 시뮬레이션 / 스피드 매칭
* **플랫폼**: 웹 브라우저 (Chrome 최신 기준, 모바일 Safari/Chrome 대응)
* **대상**: 전사 임직원 — 플레이어 및 관람자
* **개발 목적**: 게임을 즐기는 과정에서 기관의 사업과 타 부서 업무를 자연스럽게 이해하고 유대감을 형성

### 1.1 성공 지표 (Success Metrics)

목적이 달성됐는지 판단할 기준입니다. v1에는 없었습니다.

| 지표 | 목표 | 측정 방법 |
| --- | --- | --- |
| 참여율 | 대상 인원의 40% 이상 1회 이상 플레이 | 고유 참가자 수 / 전체 인원 |
| 재플레이율 | 플레이어의 50% 이상이 2회 이상 | 참가자별 라운드 수 |
| 학습 효과 | 동일 참가자의 2회차 정확도가 1회차 대비 상승 | 라운드별 정확도 비교 |
| 부서 인지도 | 전 부서 문항의 평균 정확도 60% 이상 | 부서별 정답률 집계 |
| 무결성 | 부정 의심 플래그 0.5% 미만 | §7.3 이상 탐지 |

**부서별 정답률 집계는 그 자체로 행사 후 자료가 됩니다** — "가장 많이 틀린 부서 TOP 3"는 곧 "전사가 가장 모르는 업무"이고, 시상식 슬라이드 한 장으로 쓸 수 있습니다.

## 2. 운영 시나리오

UI 설계가 갈리는 지점이라 먼저 확정합니다. v2는 **두 가지를 모두 지원**하되 기본을 A로 둡니다.

### 2.1 시나리오 A — 개인 기기 (기본)

참가자가 각자 폰/PC로 QR 또는 링크 접속 → 대기 없이 플레이 → 기록이 실시간 스코어보드에 반영.

* 장점: 동시 수용 인원 무제한, 운영 인력 최소
* 요구: 모바일 터치 조작 필수, 세로 화면 대응, 저사양 기기 대응

### 2.2 시나리오 B — 현장 부스 (병행)

행사장 PC 1~2대에서 순서대로 플레이, 대형 스크린에 관전 화면 송출.

* 장점: 관전 몰입도 높음, 결승전 진행에 적합
* 요구: 키보드 단축키 조작, 대형 화면 레이아웃, 관전 모드

### 2.3 권장 대회 포맷

```
예선 (행사 기간 상시)     시나리오 A · 개인 기기 · 1인 3회까지 · 최고 기록 채택
   ↓ 상위 8명
결승 (행사 당일 무대)     시나리오 B · 부스 PC · 단판 · 대형 스크린 관전
```

예선을 상시로 두면 참여율(§1.1)이 오르고, 결승을 무대에 올리면 관전 요소가 생깁니다. 둘 중 하나만 하면 각각 "관전 없는 대회" 또는 "참여율 낮은 대회"가 됩니다.

## 4. 게임 규칙

### 4.1 코어 루프

```
민원인 등장 → 말풍선에 민원 내용 출력 → 플레이어가 담당 부서 선택
   ├ 정답 → 점수 + 콤보 상승 → 즉시 다음 민원인
   ├ 오답 → 0.7초 스턴 + 정답 해설 노출 → 콤보 0 → 다음 민원인
   └ 시간 초과 → 민원인 이탈 → 감점 → 콤보 0 → 다음 민원인
```

* 판당 제한시간 **180초**
* 민원인은 1명씩 처리 (대기열은 시각적 압박용으로 표시)

### 4.2 점수 체계

| 이벤트 | 점수 | 콤보 |
| --- | --- | --- |
| 정답 | `100 × 콤보배수 + 속도보너스` | +1 |
| 오답 | 0 (감점 없음) | 0으로 리셋 |
| 시간 초과 이탈 | **−50** | 0으로 리셋 |
| 악성 민원인 퇴치 | **+300** | 유지 (리셋되지 않음) |
| 악성 민원인 이탈 | **−100** | 0으로 리셋 |

**콤보 배수**

| 연속 정답 | 배수 |
| --- | --- |
| 0–4 | ×1.0 |
| 5–9 | ×1.2 |
| 10–19 | ×1.5 |
| 20–29 | ×2.0 |
| 30+ | ×2.5 (상한) |

**속도 보너스**: `max(0, round(60 − 응답시간초 × 20))` — 3초를 넘으면 0.

**설계 의도**: 총점은 *정확도 × 속도 × 지속력*의 곱으로 결정됩니다. 콤보 배수가 있어 "빠르지만 자주 틀리는" 플레이보다 "조금 느려도 안 틀리는" 플레이가 유리하며, 속도 보너스가 그 반대 방향으로 균형을 잡습니다. 어느 한쪽만으로는 1등이 나오지 않게 하는 것이 목표입니다.

**오답 감점을 폐지한 이유**: v1은 오답에 감점 + 1.5초 스턴 + 콤보 리셋을 모두 부과했습니다. 스턴만으로도 이미 시간이라는 자원을 잃는 처벌이고, 여기에 감점까지 더하면 초반에 몇 번 틀린 참가자는 회복 불가능하다고 느껴 이탈합니다. 전사 임직원 대상 행사에서 이건 참여율에 직결됩니다. 대신 **시간 초과 이탈**에는 감점을 유지해 "모르면 아무거나 찍기"가 "가만히 있기"보다 낫도록 설계했습니다.

### 4.3 난이도 곡선

180초를 3페이즈로 나눕니다.

| 페이즈 | 구간 | 부서 버튼 수 | 민원 제한시간 | 악성 민원 확률 |
| --- | --- | --- | --- | --- |
| 1 · 워밍업 | 0–60초 | 6개 | 8.0초 | 0% |
| 2 · 러시 | 60–120초 | 8개 | 6.0초 | 6% |
| 3 · 오버로드 | 120–180초 | 12개 | 4.5초 | 12% |

* 부서 버튼 수는 **정답 부서 1개 + 오답 후보 N−1개**를 매 문항 샘플링해 구성합니다(전체 부서를 항상 다 띄우지 않음). 페이즈가 오르면 선택지가 늘어 난이도가 올라갑니다.
* 콤보 20 이상이면 제한시간이 추가로 10% 감소합니다 — 잘하는 참가자에게만 상단 난이도를 열어 **점수 상한을 뚫어주는 장치**입니다. 이게 없으면 상위권이 만점에 몰려 순위가 갈리지 않습니다.

### 4.4 오답 처리

* 스턴 **0.7초** (v1의 1.5초에서 단축) — 조작 불가, 화면에 "버퍼링…" 표시
* 스턴 중 **정답 부서명 + 한 줄 해설**을 노출 (§5.3)
* 감점 없음, 콤보만 리셋

1.5초는 3분 게임에서 체감이 매우 깁니다. 40회 오답 시 60초, 즉 게임의 3분의 1이 정지 화면입니다. 관전 관점에서도 치명적입니다.

### 4.5 악성 민원인 & 경영진 찬스

**등장**: 붉은 오라 + 화면 테두리 경고 + 진동(§5.5 기준 내). 일반 부서 버튼 비활성화.

**시간 소모**: 일반의 **1.5배** (v1의 2배에서 완화). 페이즈 3에서 2배는 사실상 즉사 판정입니다.

**퇴치 수단 — 3가지 경로 (데드락 차단)**

| # | 경로 | 조건 |
| --- | --- | --- |
| 1 | 경영진 찬스 버튼 | 판당 3회, 쿨타임 20초 |
| 2 | 진정 게이지 | 찬스 소진·쿨타임 중일 때 활성화. 표시되는 키를 3회 연타 |
| 3 | 자동 이탈 | 최대 10초 경과 시 자동 종료 (−100점) |

v1 규칙대로면 "찬스 3회 모두 소진 + 악성 민원인 등장 = 게임 종료까지 아무것도 못 함"이 성립합니다. 경로 2와 3이 이를 막습니다. 특히 **경로 3은 최후의 안전장치**로, 어떤 상태에서도 게임이 10초 넘게 멈추지 않음을 보장합니다.

## 5. UI / UX 요구사항

### 5.1 레이아웃

```
┌───────────────────────────────────────────────┐
│ SCORE 12,400   COMBO ×12 ▮▮▮▮▮░░   ⏱ ▮▮▮▮▮▮░░░ │  헤더
├──────────────────────┬────────────────────────┤
│                      │  [Q] 특허심사기획팀     │
│   👤 "제 특허가       │  [W] 상표디자인심사팀   │
│      거절됐는데       │  [E] 정보화사업팀       │  부서 그리드
│      어디로 가야      │  [R] 고객지원팀         │
│      하나요?"        │  [A] …                 │
│                      │  [S] …                 │
│   대기열 👤👤👤       │                        │
├──────────────────────┴────────────────────────┤
│  🎖 실장님 찬스 ×2    🏛 임원진 찬스 ×1  (20s) │  비상 대책반
└───────────────────────────────────────────────┘
```

* 모바일 세로에서는 상하 분할로 전환 (민원인 상단 / 부서 그리드 하단)
* 말풍선 텍스트는 최소 18px, 모바일 16px 이상

### 5.2 입력

| 방식 | 지원 |
| --- | --- |
| 마우스 클릭 | 전 화면 |
| 터치 | 전 화면, 최소 터치 타겟 44×44px |
| 키보드 | `Q W E R` / `A S D F` / `Z X C V` (최대 12개, 페이즈 3 대응) |
| 찬스 | `Space` (실장님) / `Shift` (임원진) |

v1은 8개 키만 명시했으나 페이즈 3에서 부서 12개를 띄우므로 3행으로 확장합니다. **키 라벨은 버튼 위에 항상 표시**합니다 — 외우게 하면 첫 플레이가 불리해집니다.

### 5.3 학습 피드백 (신규)

개발 목적인 "타 부서 업무 이해"를 실제로 달성하는 장치입니다.

* **오답 시**: 스턴 0.7초 동안 `정답: OOO팀 — <한 줄 설명>` 노출
* **게임 종료 후**: 틀린 문항 목록을 부서별로 묶어 리뷰 화면에 표시
* **종료 화면**: "오늘 새로 알게 된 부서 N곳" 카피로 학습량을 가시화

이게 없으면 참가자는 3분 동안 반사신경만 쓰고 아무것도 배우지 않은 채 나갑니다. v1의 §1(개발 목적)과 §3(기능)이 연결되지 않았던 지점입니다.

### 5.4 문제 은행 (콘텐츠 스펙)

```ts
interface Complaint {
  id: string;
  text: string;            // 민원인 대사 (40자 이내 권장)
  correctDept: string;     // 정답 부서 ID
  distractors?: string[];  // 헷갈리기 쉬운 부서 (지정 시 우선 출제)
  explanation: string;     // 오답 시 노출할 한 줄 해설 (40자 이내)
  difficulty: 1 | 2 | 3;   // 페이즈 배정용
  source?: string;         // 특허법 조문 등 근거 출처
}
```

**필요 문항 수 산정**: 1판 180초 ÷ 평균 3초 = **약 50~60문항 소비**. 3회 플레이 시 150~180문항. 중복 체감을 막으려면 **최소 200문항**이 필요합니다. v1의 "무작위로 스크립트화"는 실제로는 사람이 큐레이션해야 하는 작업량입니다.

**난이도 배분**: 난이도 1 — 40%, 2 — 40%, 3 — 20%. 페이즈별로 해당 난이도에서 우선 출제.

> ⚠️ **콘텐츠가 이 프로젝트의 최대 리스크입니다.** 코드는 만들 수 있지만 200문항의 정확한 부서 매칭은 기관 내부 지식이 필요합니다. §11-2 참조.

### 5.5 연출 안전 기준 (신규)

전사 대상 행사에서 광과민성 발작은 실재하는 리스크입니다.

| 항목 | 기준 |
| --- | --- |
| 화면 플래시 | **초당 3회 미만** (WCAG 2.3.1) |
| 스크린 셰이크 | 진폭 최대 8px, 지속 0.4초 이내 |
| 붉은 섬광 | 화면 면적 25% 이상을 채우는 순간 전환 금지 — 테두리 글로우로 대체 |
| `prefers-reduced-motion: reduce` | 셰이크·플래시 전면 비활성화, 테두리 색상 변화로만 표현 |
| 설정 | 게임 내 "연출 강도 낮추기" 토글 상시 제공 |

### 5.6 접근성

* 시간 게이지는 **색상 + 숫자 + 막대 길이** 3중 표현 (적록색각 대응)
* 모든 인터랙션 요소 키보드 도달 가능, 포커스 링 표시
* 대비비 4.5:1 이상

## 6. 관전 및 대회 운영 (신규)

v1에 "관람자"가 대상 고객으로 명시됐지만 관련 기능 요구사항이 전혀 없었습니다.

### 6.1 스코어보드 화면 `/board`

행사장 대형 스크린 전용. 조작 없이 상시 송출.

* 실시간 TOP 20 (순위 변동 시 행 이동 애니메이션)
* 방금 갱신된 기록 하이라이트 + 부서명 표시
* 현재 플레이 중인 인원 수, 누적 참가자 수
* 부서별 평균 정답률 티커 (하단 흐름)

### 6.2 관전 모드 `/spectate/:roundId`

결승 진행용. 플레이어 화면을 지연 1초 이내로 미러링하고, 해설자용 정보(현재 콤보, 정답률, 남은 찬스)를 오버레이합니다.

### 6.3 운영자 콘솔 `/admin`

* 대회 상태 전환 (예선 / 결승 / 종료)
* 부정 의심 기록 검토 및 무효 처리
* 문항 정답률 실시간 확인 (난이도 이상 문항 즉시 비활성화)
* 스코어보드 수동 새로고침

행사 당일 문제가 터졌을 때 **코드 수정 없이 대응할 수 있는 수단**이 반드시 필요합니다.

## 7. 무결성 — 부정행위 방지 (신규 · 최우선)

> v1: "게임 종료 즉시 플레이어의 사번/성명과 최종 스코어를 백엔드 DB로 전송"

**이 구조는 브라우저 콘솔에서 `fetch('/api/score', {body: JSON.stringify({score: 999999})})` 한 줄로 무너집니다.** 참가자가 전원 개발자인 사내 개발자 행사에서, 상품이 걸린 순위표를 이 방식으로 운영할 수 없습니다. 누군가는 반드시 시도하고, 성공하면 대회 자체가 무의미해집니다.

### 7.1 서버 권위 채점

```
1. 라운드 시작   POST /api/rounds
   서버 → seed, 문항 시퀀스(ID만), roundToken(HMAC 서명, 5분 만료, 1회용)

2. 플레이        클라이언트는 시퀀스대로 진행하며 입력 로그를 누적
                 [{ questionId, chosenDept, elapsedMs }, ...]

3. 라운드 종료   POST /api/rounds/:id/submit  (roundToken 포함)
                 서버가 로그를 재생(replay)하여 점수를 재계산
                 → 클라이언트가 보낸 점수는 참고용으로만 저장, 순위에는 서버 점수만 사용
```

**핵심**: 클라이언트는 "무엇을 눌렀는지"만 보고하고, "몇 점인지"는 서버가 정합니다. 점수 필드를 조작해도 무시됩니다.

### 7.2 검증 규칙

| 검사 | 기준 | 위반 시 |
| --- | --- | --- |
| 토큰 유효성 | 서명 일치, 미사용, 5분 이내 | 거부 |
| 소요 시간 대조 | 서버 기준 경과 시간과 로그 총합의 차이 ±3초 이내 | 거부 |
| 문항 시퀀스 일치 | 발급한 순서와 동일 | 거부 |
| 총 시간 상한 | 로그 총합 ≤ 180초 + 여유 | 거부 |

### 7.3 이상 탐지 (자동 플래그)

거부까지는 아니지만 운영자 검토 대상으로 표시합니다.

* 평균 응답 시간 < 150ms 가 10문항 이상 연속
* 정확도 100% + 응답 시간 표준편차 < 30ms (자동화 의심)
* 동일 사번 해시로 1분 내 3회 이상 제출

### 7.4 남는 한계 (명시)

서버 권위 채점으로도 **매크로(화면 인식 후 자동 클릭)** 는 막지 못합니다. §7.3의 통계적 탐지 + 결승을 현장 부스 PC(§2.2)에서 진행하는 운영으로 보완합니다. **상품이 걸린 최종 순위는 현장 결승으로 결정하는 것을 강력히 권장합니다.**

## 8. 개인정보 처리 (신규)

> v1: "플레이어의 사번/성명과 최종 스코어를 백엔드 DB로 전송 및 실시간 전사 스코어보드 갱신"

사번과 성명은 개인정보이며, 사내 행사라도 개인정보보호법이 적용됩니다. 공개 스코어보드에 실명을 띄우는 것은 별도 동의 사안입니다.

| 항목 | 수집 | 저장 | 공개 |
| --- | --- | --- | --- |
| 사번 | 필요 (중복/본인확인) | **HMAC 해시만** 저장, 원문 미저장 | ❌ |
| 표시명 | 필요 | 평문 | ✅ (참가자가 닉네임/실명 선택) |
| 부서 | 선택 | 평문 | ✅ |
| 게임 기록 | 자동 | 평문 | ✅ (점수만) |

* 첫 접속 시 **수집 항목·목적·보관기간 고지 후 동의** 체크
* 보관기간: **행사 종료 후 30일 내 파기** (시상 이의제기 기간 고려)
* 표시명 기본값은 닉네임 입력을 권장하되, 실명 공개를 선택할 수 있게 함

## 9. 기술 아키텍처

### 9.1 스택

| 레이어 | 선택 | 비고 |
| --- | --- | --- |
| Frontend | React 18 + TypeScript + Tailwind CSS + Vite | v1의 Phaser.js 대신 DOM/CSS. 이 게임은 스프라이트 물리 연산이 없어 게임 엔진이 불필요하며, DOM이 접근성(§5.6)·번들 크기·유지보수에서 유리 |
| Backend | Node.js 20 + Fastify + TypeScript | |
| DB | PostgreSQL (Supabase 또는 Cloud SQL) | 저장소 인터페이스로 추상화해 교체 가능하게 |
| 실시간 | Supabase Realtime 또는 SSE | 스코어보드 전용 |
| 배포 | Docker (`Dockerfile`, `docker-compose.yml`) | §9.4 |

### 9.2 데이터 모델

```sql
players       (id, employee_hash UNIQUE, display_name, dept, consented_at, created_at)
rounds        (id, player_id, seed, question_ids[], token_hash, issued_at,
               submitted_at, server_score, client_score, accuracy, max_combo,
               status, flags[])
answers       (id, round_id, question_id, chosen_dept, correct, elapsed_ms)
questions     (id, text, correct_dept, distractors[], explanation, difficulty, active)
```

`answers`를 문항 단위로 남기면 §1.1의 부서별 정답률과 §5.3의 오답 리뷰가 추가 작업 없이 나옵니다.

### 9.3 API

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| `POST` | `/api/players` | 동의 + 표시명 등록, 사번 해시 |
| `POST` | `/api/rounds` | 라운드 시작 — seed·시퀀스·토큰 발급 |
| `POST` | `/api/rounds/:id/submit` | 입력 로그 제출 → 서버 채점 |
| `GET` | `/api/leaderboard` | 상위 N + 본인 순위 |
| `GET` | `/api/stats/departments` | 부서별 정답률 |
| `GET` | `/api/admin/flagged` | 부정 의심 목록 (인증 필요) |

### 9.4 배포

v1은 "정적 `index.html` 하나로 구동" 과 "Node 백엔드 + Supabase" 와 "Docker/GCP 패키징 필수"를 동시에 요구해 서로 충돌했습니다. v2는 다음과 같이 정리합니다.

* **정식 배포**: `docker-compose up` 한 번으로 프론트(정적 서빙) + 백엔드 + DB 기동. 주최측 GCP 인프라 요건 충족.
* **보조 배포**: 동일 소스를 Vercel에도 배포해 예선용 상시 링크로 사용 (현행 `minwon-connection-god.vercel.app` 유지).
* **오프라인 폴백**: 백엔드 연결 실패 시 로컬 스토리지에 기록하고 게임은 계속 진행. 복구 후 동기화. **행사 당일 네트워크는 반드시 문제를 일으킵니다.**

### 9.5 부하 산정

라운드당 API 호출 3회(등록 1 + 시작 1 + 제출 1). 동시 100명 기준 피크 약 10 req/s — 일반적인 단일 인스턴스로 충분합니다. 실시간 구독은 스코어보드 화면만 사용해 커넥션 수를 억제합니다.
