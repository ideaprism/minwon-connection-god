# 민원 연결의 神 (KIPI COMPLAINT MASTER)

한국특허정보원 사내 e-sports 행사용 민원 라우팅 게임입니다.
민원 내용을 읽고 담당 부서로 77초 안에 최대한 많이 연결하며, 플레이 과정에서
기관의 사업과 타 부서 업무를 자연스럽게 익히는 것을 목적으로 합니다.
라운드 길이는 `shared/src/rules.ts`의 `ROUND_DURATION_SEC` 하나로 정해집니다.

**배포:** https://minwon-connection-god2.vercel.app — `main`에 push하면 자동으로
갱신됩니다. 빌드 명령과 출력 경로는 `vercel.json`에 있습니다.

## 실행

Node.js LTS만 있으면 됩니다(https://nodejs.org).

**가장 쉬운 방법** — Windows는 `start.bat` 더블클릭, macOS·Linux는 `./start.sh`.
패키지 설치부터 브라우저 열기까지 알아서 합니다.

**명령으로 실행할 때:**

```bash
npm install      # 처음 한 번. shared 빌드까지 자동으로 끝난다
npm run dev      # 게임 (http://localhost:5173)
npm run dev:api  # 백엔드 (http://localhost:8787) — 없어도 게임은 돌아간다
npm run build    # shared + backend + frontend 빌드
npm test         # 서버 검증 로직 테스트
```

`frontend`는 `shared`의 **빌드 결과물**(`shared/dist`)을 참조합니다. 그래서
`npm install`의 postinstall과 `npm run dev`가 매번 `shared`를 먼저 빌드합니다.
`shared/src`를 고쳤다면 dev 서버를 다시 띄우거나 `npm run build -w shared`를
실행해야 반영됩니다.

프론트 개발 서버는 `/api`를 8787로 프록시합니다. 운영에서는 한 프로세스가 API와
정적 파일을 함께 서빙해 같은 출처가 되므로, 프록시는 그 배치를 개발에서 흉내내는
것입니다. 백엔드를 다른 포트로 띄웠다면 `API_TARGET`으로 덮어씁니다.

백엔드 없이도 게임은 돌아갑니다. 서버가 없으면 기록이 브라우저에만 남고
순위에는 반영되지 않는다고 화면에 표시됩니다.

### Docker

```bash
cp .env.example .env    # APP_SECRET · ADMIN_TOKEN · DB_PASSWORD 채우기
docker compose up -d    # http://localhost:8787
```

컨테이너 하나가 API와 프론트 정적 파일을 함께 서빙합니다.

## 구성

| 경로 | 설명 |
| --- | --- |
| `docs/PRD.md` | 제품 요구사항 정의서 v2 |
| `shared/src/rules.ts` | 게임 규칙 — 점수·페이즈·리플레이 채점 |
| `shared/src/round.ts` | 출제 계획 — 시드로 문항 시퀀스를 만든다 |
| `shared/src/data/` | 문항·분류 데이터. `complaints.ts`·`departments.ts`는 생성물 |
| `backend/src/verify.ts` | 라운드 토큰과 제출 로그 검증 |
| `backend/src/routes.ts` | API |
| `frontend/src/game/useGame.ts` | 라운드 상태 머신 |
| `frontend/src/game/deptGroups.ts` | 부서 버튼을 본부·센터·단으로 묶는 규칙 |
| `frontend/src/App.tsx` | 랜딩 / 게임 / 결과 화면 |
| `docs/문제은행_v5.xlsx` | 문제 은행 원본 — 문항 추가·수정은 여기서 |
| `scripts/import_bank.py` | 문제 은행 → 게임 데이터(TS) 생성 |

`shared`가 프론트와 백엔드 양쪽에서 쓰이는 것이 설계의 핵심입니다.
클라이언트는 화면을 그리려고, 서버는 제출된 입력 로그를 재생해 점수를 다시
계산하려고 같은 함수를 씁니다(PRD 7장). 규칙을 고칠 때는 반드시 `shared`만
고쳐야 양쪽이 어긋나지 않습니다.

## 무결성

점수는 서버가 정합니다. 클라이언트는 "무엇을 눌렀는지"만 보고하고, 서버가
같은 규칙 엔진으로 다시 계산합니다. 실제로 확인한 결과:

| 시도 | 결과 |
| --- | --- |
| 점수 999999 전송 | 서버가 로그를 재생해 687점으로 확정 |
| 같은 토큰 재제출 | 409 `token_used` |
| 발급되지 않은 문항 제출 | 422 `sequence_mismatch` |
| 토큰 위조 | 401 `invalid_token` |
| 흐른 시간보다 오래 플레이했다고 주장 | 422 `impossible_timing` |

남는 한계는 매크로입니다. 통계적 이상 탐지(`fast_streak`, `robotic_timing`)로
운영자 검토 대상만 표시하며, **상품이 걸린 최종 순위는 현장 결승으로 결정하는
것을 권장합니다**(PRD 7.4).

### v4 → v5

분류체계가 두 군데 바뀌었습니다.

| 변경 | 내용 |
| --- | --- |
| 분리 | `특허정보 번역서비스` → `PCT 국제출원문서 번역`(6문항) + `한영 기계번역(K2E-PAT)`(9문항) |
| 제외 | `지식재산 통계서비스` — 존속 여부 확인 중이라 게임에서 뺍니다 |

v4에서 "번역서비스 부서 재확인"으로 남아 있던 숙제가 정리된 것입니다. 사업
페이지의 담당부서와 실제 수행부서가 다른 사례가 있어, 수행 주체 기준으로
나눴습니다.

⚠️ 새 두 분류는 문항이 각각 6개·9개로 얇습니다. 부서 버튼은 항상 14개가 모두
떠 있으므로 이 두 분류는 같은 문항이 자주 돌아옵니다. 리허설에서 체감을 확인하고
필요하면 엑셀에서 보강하십시오. 생성 스크립트가 10개 미만 분류를 경고합니다.

문항을 고친 뒤에는 다시 생성하십시오.

```bash
python3 scripts/import_bank.py    # 엑셀 → departments.ts / complaints.ts
```

`shared/src/data/complaints.ts`와 `departments.ts`는 생성물입니다. 직접 고치면
덮어써집니다. 같은 디렉터리의 `evilComplaints.ts`는 엑셀에서 나오지 않는 손으로
쓴 파일이므로 여기서 고칩니다.

### 게임에 넣는 기준

- 분류체계 시트의 `게임 노출`이 `노출`인 분류만
- `검수상태`가 `검수완료`인 문항만

보류 문항을 빼는 이유는 이 게임이 오답 시 해설을 그대로 띄워 참가자를
학습시키기 때문입니다. 확인되지 않은 내용을 가르치면 안 됩니다. 확인이 끝나
검수완료로 바꾸면 다음 생성 때 자동으로 합류합니다.

### 남은 작업

- **보류 14문항 확인** — 지식재산 통계서비스 7문항(존속 여부), KIPRIS NPL 검색,
  Open API 인증키 절차, R&D 도면 유사 추출, 외국어 상담·상담 이력, 국제협력 수치.
  통계서비스가 존속으로 확인되면 분류체계 시트의 `게임 노출`을 `노출`로 되돌리십시오
  (게임 내부 ID `statistics`는 스크립트에 남겨 두었습니다)
- **번역 두 분류 문항 보강** — `PCT 번역` 6문항, `K2E-PAT` 9문항으로 얇습니다
- 난이도 분포는 참고선으로만 운용 (현재 47 : 97 : 42)
